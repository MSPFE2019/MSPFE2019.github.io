02 · What ships

Explore the component toolbox

Filter by the part of the platform you are packaging. Each card explains why the component earns a place in a solution and when to reach for it.

Data

Tables and columns

Why: Create a governed, relational source of truth. When: Use for business data that must be secured, searched, audited, and reused.

Data

Relationships and keys

Why: Preserve business meaning and record integrity. When: Use when records have parent-child, many-to-many, or integration identity relationships.

Data

Dataflows and virtual tables

Why: Reuse ingestion logic or expose external data without copying it. When: Use for repeatable imports or systems that remain authoritative elsewhere.

Experience

Apps and custom pages

Why: Give each audience the right task-focused experience. When: Use model-driven apps for process-heavy data and canvas pages for tailored interactions.

Experience

Forms, views, charts, and dashboards

Why: Make the same data understandable and actionable. When: Use when users need role-specific entry, filtering, monitoring, or trend analysis.

Experience

Web resources and PCF controls

Why: Fill a deliberate UX gap with reusable assets. When: Use only when standard controls cannot provide the required behavior or presentation.

Experience

Power Pages components

Why: Extend governed business data to external users. When: Use for authenticated or public self-service portals with carefully designed table permissions.

Automation

Cloud flows and child flows

Why: Automate repeatable work and notifications. When: Use flows for orchestration, approvals, scheduled work, and reusable actions across apps.

Automation

Business process flows

Why: Make a human process visible and consistent. When: Use when users progress through known stages and need guidance rather than full automation.

Automation

Plug-ins and custom APIs

Why: Enforce transactional rules close to the data. When: Use for synchronous validation, complex server-side logic, or reusable operations that flows cannot safely provide.

Configuration

Environment variables

Why: Keep deployment-specific values out of logic. When: Use for URLs, IDs, feature flags, and settings that differ across development, test, and production.

Configuration

Connection references

Why: Make flow connections replaceable during deployment. When: Use whenever a solution flow depends on a connector or service account.

Configuration

Publisher and managed properties

Why: Establish ownership and control customization. When: Define them before building and use managed properties when distributing a controlled product.

Integration

Custom connectors

Why: Give apps and flows a reusable API contract. When: Use for a private or partner API that lacks a suitable standard connector.

Integration

Service endpoints

Why: Deliver Dataverse events to an integration boundary. When: Use for event-driven integrations that need server-side delivery rather than user-triggered automation.

Integration

Email and document templates

Why: Standardize customer-facing output. When: Use when messages or documents must be consistent, localized, and maintained centrally.

Security

Security roles

Why: Apply least-privilege access to tables and actions. When: Define roles whenever different job functions need different data boundaries.

Security

Field security profiles

Why: Protect sensitive columns and sharing patterns. When: Use for confidential fields, access teams, queues, and controlled record collaboration.

AI

AI Builder assets

Why: Add targeted intelligence to business processes. When: Use for extraction, prediction, classification, or prompt-based assistance where value and governance are clear.

AI

Copilot Studio assets

Why: Make approved business knowledge and actions conversational. When: Use when an agent can safely answer questions or perform bounded tasks through governed tools.

03 · Worked example

A well-designed solution in practice

Imagine a “Service Request Operations” solution for an internal support team. It uses components because each one has a clear job—not because the solution can hold them.

Service Request Operations

Employees submit requests, agents triage and resolve them, managers monitor service levels, and an agent answers common questions. The solution is split into a reusable foundation and an application layer so future apps can share the same data and security model.

Design rule: use the simplest component that meets the requirement, keep configuration outside code, secure data at the platform boundary, and avoid direct production customisation.
Dataverse tables + security rolesRequests, categories, teams, SLAs, and least-privilege access
↓

↓
Flows + connection referencesNotifications, approvals, escalations, and environment-safe connections
↓
Environment variables + AI agentService URLs, feature flags, and bounded self-service answers
04 · Deployment strategy

Unmanaged or managed?

Both belong in a mature ALM story. The distinction is where editing is allowed and how the package is removed or upgraded.

Development

Unmanaged solutions

  • Editable in the target environment
  • Best for authoring and debugging
  • Changes can be layered by other solutions
Test and production

Managed solutions

  • Controlled package boundary
  • Supports upgrades and clean removal
  • Reduces accidental direct customisation
